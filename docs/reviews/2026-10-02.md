## 3. What broke and how it was fixed

**Why the May runs failed**

- **Trivy.** The blocking step used `format: sarif`. In that mode trivy-action **drops the
  `severity` filter** unless `limit-severities-for-sarif` is set (confirmed in the action's
  `entrypoint.sh`). So `exit-code: 1` fired on any CVE at any severity. The base image always
  has LOW/MEDIUM findings, so the gate could never pass. Fixed: a table-format step blocks on
  CRITICAL, and a separate SARIF step reports everything without blocking.
- **SonarCloud.** `SONAR_TOKEN` was never set (`gh secret list` is empty). The annotation said
  so: "Running this GitHub Action without SONAR_TOKEN". The action
  (`sonarcloud-github-action@master`) is also deprecated. Fixed: `sonarqube-scan-action` v8.3.0,
  and an explicit step that fails with a clear message when the secret is missing.
- **Both, coming next:** all actions ran on Node 20, which left the runners on 2026-09-16.
  Bumped to Node 24 majors and pinned to commit SHAs.

**Broke during this session**

- The first "vulnerable image blocks" test exited 1 because the **build** failed (Flask 3.1
  needs Python 3.9+), not because Trivy found anything. Caught it before counting it. The bad
  fixture now uses the old May pins, and the proof scripts abort on build errors.
- `git apply -R` couldn't revert the planted Sonar patch (CRLF vs LF). The content was already
  restored, but the script now backs up and restores the file byte for byte.
- `run_scan` read `PIPESTATUS` after `|| true`, which could hide a failed scan. Rewritten to
  capture the exit code directly.
- First ZAP run on the hardened app failed on rule 10055: `base-uri` and `form-action` have no
  `default-src` fallback. Added both to the CSP (test first).
- zizmor: `actions/checkout` left the token in `.git/config` in every job, and two `run:` blocks
  expanded `${{ env.* }}` into shell. Both fixed.
- The Terraform `user_data` template wasn't covered by `.gitattributes`. A Windows checkout
  would have given it CRLF and broken the boot script on Linux. Fixed.

## 4. Decisions made on your behalf

Confirm or reverse each one.

1. **Trivy blocks on CRITICAL, including unfixed CVEs.** No `ignore-unfixed`. Both CRITICALs in
   the EOL test image were `will_not_fix`; with `ignore-unfixed` that image would pass. HIGH
   stays report-only (44 unfixable HIGHs today would block every build).
2. **Base image pinned by digest** (`python:3.11-slim-trixie@sha256:e416...`) with Dependabot
   to move it. Reproducible scans, but you must merge Dependabot PRs to get base fixes.
3. **`apt-get upgrade` in the final stage, pip/setuptools/wheel removed.** Cuts 7 fixable Debian
   HIGHs and 2 Python ones. Downside: rebuilds aren't byte-identical (see section 5).
4. **ZAP gate = any High-risk alert OR any FAIL-listed rule.** CLAUDE.md says "fail on
   HIGH/CRITICAL", the phase-3 spec says "fail until headers are added". ZAP rated the bare
   app's worst finding Medium, so High-only would never block. The FAIL list is the headers
   the app promises plus server version leaks.
5. **ZAP runs from its Docker image** (digest-pinned) through `scripts/zap-scan.sh`, not
   `zaproxy/action-baseline`. Same command locally and in CI.
6. **OIDC role instead of access keys** (the phase-4 doc said keys). Trust pinned to `main` of
   this repo.
7. **CI never runs Terraform.** You apply infra from the runbook; the CI role can only push to
   the ECR repo and run SSM on the instance. Phase 5's diagram has "Terraform Apply" in the
   pipeline. I'd keep it out; your call.
8. **No SSH at all; SSM instead.** Port 5000 open to `0.0.0.0/0` by default (it's a public demo);
   set `app_ingress_cidrs` to lock it down. Egress HTTPS only, with one documented Trivy ignore.
9. **No phase marked ✅.** New status keys: 🧪 proven locally, CI pending; 🔧 built offline,
   AWS pending. CLAUDE.md said mark finished phases ✅. None is finished until CI proves it.
10. **Deploy job gated three ways:** manual dispatch, `main` only, repo variable
    `AWS_DEPLOY_ENABLED=true`. It also checks the three gate workflows passed for that commit.
11. **Deps:** flask 3.1.3, werkzeug 3.1.9, gunicorn 26.2.0 (latest at the time). Python stays 3.11.
12. **Sonar CSRF finding (S4502) left open.** Stateless JSON API, no cookies or sessions. Mark it

## 6. How to explain it in an interview

1. "Each gate has a test that feeds it something bad and checks it blocks. The first time I
   ran that, a 'block' turned out to be a failed build. That's why the scripts stop on errors."
2. "The Trivy gate looked like 'block on CRITICAL' but blocked on everything, because SARIF
   output mode drops the severity filter. I split it: one step enforces, one step reports."
3. "I don't ignore unfixed CVEs. An end-of-life base image is mostly 'will not fix', so
   ignoring them would let the worst image through."
4. "ZAP rates missing headers Low or Medium. I didn't lower the threshold for everything. I
   made the headers the app promises mandatory and kept 'High blocks' for the rest."
5. "CI deploys with a one-hour OIDC credential that only works from main. It can push one
   image and run one command on one instance. It can't change infrastructure."
